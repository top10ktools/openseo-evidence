# Maintenance and product roadmap

Last updated: 2026-09-13

This document is the durable handoff for future OpenSEO Evidence maintenance. The product promise is local-first analysis: imported search data and generated reports stay inside the browser. New features must preserve that promise unless a future major version clearly changes the architecture and obtains explicit owner approval.

## Current release baseline

- Version: 0.1.0
- Production: <https://top10ktools.github.io/openseo-evidence/>
- Repository: <https://github.com/top10ktools/openseo-evidence>
- Runtime: static HTML, CSS and JavaScript; zero runtime dependencies
- Inputs: GSC and Bing Webmaster Tools CSV exports
- Outputs: evidence-ranked CSV, JSON and Markdown
- Release gate: 18 deterministic tests, build, privacy scan, artifact checksums and real-Chromium network interception
- Independent release verdicts: correctness GO and privacy/security GO

## Architecture boundaries

- `src/core.js`: parsing, normalization, scoring and exports; keep it DOM-free and deterministic.
- `src/worker.js`: isolated analysis worker; keep heavy processing off the UI thread.
- `src/app.js`: browser interaction only; never add upload, analytics, telemetry or remote API calls silently.
- `dist/`: reproducible static release generated by `npm run build`; do not hand-edit it.
- CSP must retain `connect-src 'none'` while the zero-network promise applies.
- Google and Bing metrics remain separate. Cross-engine findings may compare evidence but must not average incompatible metrics.
- Evidence, confidence, provenance and limitations are product requirements, not decorative metadata.

## Release procedure

1. Create a feature branch and update tests with the implementation.
2. Run `npm run check`.
3. Run `(cd dist && sha256sum -c SHA256SUMS)`.
4. Run `scripts/browser-network-check.mjs` with external Playwright and Chromium paths. Import both fixtures, analyze and trigger all exports; allow only the packaged worker assets and require zero external/unapproved requests.
5. Review privacy architecture, threat model, methodology, README and SBOM when behavior changes.
6. Merge to `main`; GitHub Actions must pass and Pages must deploy successfully.
7. Verify the public page and record meaningful behavior changes in a GitHub release.

Never commit `.env`, tokens, production GSC/Bing exports or user-generated reports. Never place a token in a Git remote URL.

## Prioritized roadmap

### P0 — release hardening

- Add the Chromium privacy gate to CI with a pinned Playwright development version and dependency lockfile, while keeping `dist` dependency-free.
- Add parser fixtures for more GSC/Bing locales and documented export variants.
- Add visible sample data and an interactive product tour using synthetic data only.
- Add a release changelog and signed/tagged releases with checksum artifacts.

### P1 — highest-value SEO workflow features

- Period comparison chosen by the user, including explicit date windows and minimum-coverage warnings.
- Filters and sortable views for engine, opportunity type, confidence, query and page.
- Saved local workspace using IndexedDB, encrypted/exportable where practical, with a clear delete-all control.
- Keyword clustering and intent labels computed locally with deterministic rules; no hidden external AI calls.
- Action backlog fields: owner, priority, status, notes and local import/export.
- Page/query drill-down with supporting observations and calculation trace.
- Automated validation of GSC and Bing export scope before cross-engine comparison.

### P2 — advanced local analysis

- Statistical significance and effect-size guidance for CTR experiments.
- Brand/non-brand segmentation from a user-maintained local rule set.
- Device, country and search-appearance dimensions when present in exports.
- Cannibalization history and consolidation suggestions with conservative evidence thresholds.
- Local crawl import to join title, canonical, status, indexability and internal-link evidence.
- Optional GA4 CSV import for landing-page engagement reconciliation without API access.

### P3 — ecosystem and adoption

- Installable PWA with offline verification and explicit cache-reset controls.
- CLI companion that uses the same core engine and writes no telemetry.
- Reusable JSON schema for evidence reports and documented integrations.
- Translations, starting with Vietnamese, while preserving English as the canonical documentation language.
- Public synthetic benchmark corpus and reproducible accuracy/performance measurements.

## Feature acceptance checklist

A feature is ready only when it has deterministic fixtures, handles malformed/adversarial input within safety limits, preserves spreadsheet/HTML injection defenses, documents metric semantics and limitations, does not weaken CSP or the no-upload promise, keeps the UI responsive, produces reproducible exports and passes independent correctness/privacy review proportional to risk.

## Known residuals

- The UI is memory-bound and capped at 20 files / 200 MB total / 100 MB per file.
- Warning output intentionally shows up to 25 detailed warnings plus a truncation summary.
- Very large adversarial inputs can accumulate internal ambiguity warnings before result truncation.
- Date decay is conservative and requires adequate contiguous daily observations; it is not a causal model.
- ZIP imports, OAuth and direct GSC/Bing API connections are intentionally excluded from v0.1.0.

## Upgrade decision rule

Prioritize additions that reduce the time between export and a defensible SEO action. Reject dashboard-only features, unverifiable scoring, covert network dependencies and features that duplicate mature products without strengthening privacy or evidence quality. Every roadmap item must be validated with real user pain before implementation.
